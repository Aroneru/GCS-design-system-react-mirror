The Variant Prop

A design-system component is its public interface. Today you design your first good one.

You already know how to make a component that works. A design-system component has a higher bar: strangers on your team must be able to use it correctly without reading its source. That makes the props API — not the internal JSX — the actual product you're shipping.

The single most common mistake is boolean-prop soup: adding a new boolean every time you want a new look. Let's see why it fails and what to do instead.

The problem: booleans don't scale

✗ Boolean soup

<Button primary />
<Button secondary />
<Button ghost outlined />

// What does this even mean?
<Button primary ghost />

✓ One variant prop

<Button variant="primary" />
<Button variant="secondary" />
<Button variant="ghost" />

// Impossible states are unrepresentable

With booleans, n looks create 2ⁿ combinations — most of them nonsense (primary and ghost?). A single variant string makes the choices mutually exclusive and, in TypeScript, gives you autocomplete plus a compile error for typos. As the Spectrum UI guide puts it: "Boolean props lock you into two states forever."1

Principle Prefer a closed set of named variants over booleans whenever a component has more than two mutually-exclusive states. It documents intent, prevents invalid combinations, and leaves room to grow (variant="danger" later).

The canonical shape

Here is the pattern you'll reuse for almost every component. Three moves make it design-system-grade:

// 1. Extend the native element → consumers get onClick, disabled, type, aria-* free
type ButtonProps = React.ComponentPropsWithoutRef<"button"> & {
  variant?: "primary" | "secondary" | "ghost";
  size?: "sm" | "md" | "lg";
};

export function Button({
  variant = "primary",   // 2. sensible defaults → the common case needs no props
  size = "md",
  className,
  ...rest                // 3. spread the rest → don't re-implement the DOM
}: ButtonProps) {
  return (
    <button
      className={`ds-btn ds-btn--${variant} ds-btn--${size} ${className ?? ""}`}
      {...rest}
    />
  );
}

Why each move matters:

  • Extend the native element. ComponentPropsWithoutRef<"button"> means every real button attribute already works — you never re-declare onClick or disabled.2
  • Defaults. <Button>Save</Button> just works. Defaults are the difference between a component people enjoy and one they configure.3
  • Spread ...rest. Consumers can pass anything native without you predicting it. Merging className (not overwriting) lets them extend styling.

Your win: build it in the repo

Turn knowledge into a skill. In your design-system-react project:

  1. Create src/components/Button/Button.tsx with the shape above.
  2. Add a Button.css with a .ds-btn base and one rule per --variant/--size (plain CSS is fine — tokens come in a later lesson).
  3. Render three buttons in App.tsx: one primary, one ghost, one disabled — passing disabled without adding a prop for it proves your ...rest works.
